# 配置与存储重构方案

状态：实施中。目标版本：Plus7z 0.2.4 / Cardo 0.2.0。

## 评估与边界

现有设置、外观、语言、历史与更新恢复记录分散在 JSON/文本文件中。单文件替换已有原子性，但一次设置保存跨多个文件，历史的读改写也没有跨进程事务。采用三种介质，各自只有一份权威数据，不提供任意切换后端的抽象。

| 介质 | 负责 | 不负责 |
| --- | --- | --- |
| TOML | 低频、可手工编辑的声明式配置：语言、主题、字体、快捷键、行为和集成选项 | 历史、任务进度、更新恢复日志 |
| JSON | GitHub API、进程命令、构建清单、显式数据交换和旧文件导入；SQLite 中不需检索的结构化状态载荷 | 新增的实时配置文件、整份历史文件 |
| SQLite | 需要事务的本地运行数据：有序历史、最近解压目录、更新准备/结果、迁移标记 | 密码、日志、压缩包内容、用户可编辑配置、Windows 注册表 |

SQLite 适合低写入并发的本地应用；引入它是为事务与可演进的数据结构，不因当前 20 条历史宣称性能提升。配置继续保留文本格式。日志仍使用滚动日志；临时文件仍由 tempfile 管理；注册表仍由平台模块按归属操作。敏感凭据不存入这三种介质，需要时由产品接入系统凭据库。

## Cardo 基础设施

1. 保留带路径上下文的原子文件 I/O，明确定位为文件与交换数据工具。
2. 提供 TOML 配置快照：类型化反序列化；同目录临时文件、sync、原子替换；跨进程写锁；保存时比较读入的原文，外部修改产生冲突，不覆盖。通过 toml_edit 只更新变化字段，保留无关字段和注释。
3. 提供 SQLite 数据库：bundled SQLite、每次操作独立连接、5 秒 busy timeout、WAL、synchronous=FULL、foreign_keys=ON；写操作使用 IMMEDIATE 短事务。异步调度由产品负责，数据库不依赖 GPUI。
4. 产品提供固定 application_id 和顺序迁移 SQL；事务内推进 user_version。拒绝未知归属和高于当前支持的 schema。已有数据库升级前使用 SQLite 在线备份；提供按需完整性检查与备份接口。不静默删除、重建或降级损坏数据库。

## p7z 接入

- 新目录：`%LOCALAPPDATA%\p7z`。`settings.toml` 是配置唯一来源，含 `schema_version = 1`；`state.sqlite3` 是运行数据唯一来源。
- 配置读取顺序：代码默认值 → TOML 已提供字段 → 本次启动显式 `--lang`（仅运行时）。不引入隐藏环境变量覆盖或热重载。手工修改后重启；运行中修改会使旧快照保存失败。
- 配置一次保存包含行为、外观、语言和主题。类型与产品语义验证后才落盘。TOML 无 null，取消快捷键明确表示为 `"disabled"`；缺省键继续使用默认绑定。
- 历史采用关系表，路径唯一、有序、最多 20 条；Remember/Remove/Clear 在同一事务中完成。缺失路径清理由后台请求负责。
- 更新计划/结果使用 SQLite 中的 JSON 载荷，复用现有类型和校验；更新助手与主程序共享数据库，完成结果和清除计划可放在同一事务中。最近解压目录也归入运行状态。
- 配置文件与 SQLite 之间不存在跨介质事务：启动迁移按可重入步骤处理，业务上不将两者拼成一个假事务。注册表和文件系统操作仍独立报告失败。

## 旧数据与失败处理

首次启动读取 `%LOCALAPPDATA%\7zplus-rust` 中现有配置、历史和最近解压目录，先完成解析与语义验证，再写入新存储。仅缺失视为默认；拒绝读取失败和格式损坏。旧文件不改写、不删除。新配置存在时优先使用；SQLite 导入与完成标记同事务提交，重复启动不覆盖新数据。迁移中断后重试，已经写入的新配置保留。

旧版未完成更新涉及旧可执行文件名，必须先用旧版完成恢复；不把它导入新更新器。旧版与新版不双写；迁移前关闭旧版。由于发行包改名，旧版本需手动升级。

数据库备份使用 SQLite backup API，不能直接复制正在写入的主文件。恢复时先退出主程序及更新助手，保留失败库和 WAL/SHM，确认备份版本再替换；不自动抹掉错误证据。TOML 保存保留上一份有效原文备份，解析错误时不自动回退，以免隐藏用户配置问题。

- 在线备份：<https://www.sqlite.org/backup.html>，一致性快照。
- rusqlite：<https://docs.rs/rusqlite/0.40.2/rusqlite/>。
